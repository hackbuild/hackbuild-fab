# Checks

Version 4, 2026-10-04. Part of the hackbuild-fab plan set; PLAN.md is the index.

This file is the registry of record for check ids, titles, families, legal
kinds, severities and origins. PLAN.md section 8 states the decisions; the
milestone cards (milestones/M-1 to M16) hold what a builder runs; this file
holds what every check is and why it exists. Where a milestone card names a
check id or title differently, this file wins and the card renumbers before
anything registers (milestones/M04-checks-project.md, M04-T12 step 1).

Conventions. hbf (working name) is the binary with CLI, MCP and HTTP
transports. CHASE (working name) is the typed design document. PIP (was
HAFT) is the published print-in-place controller at hackbuild/pip-controller
(D-013). Every number carries a qualifier (measured, computed, vendor,
inferred, unknown) and a source (D-007). Counts are as of 2026-10-04;
generated by tools/counts.mjs from M-1 onward (D-010); a count typed here is
a seed for that tool and loses to it. Repo paths are relative to the
hackbuild-fab root; evidence paths are absolute.

## 1. What a check is

A check is a registry entry that proves one declaration against Part IR (or
against exported bytes, source text, a rendered page or the whole project)
and returns evidence: the measured value, the legal values, the constraint
that set them, and where the check came from. The model writes
declarations; the tool proves them. A check never decides by itself what
the design should be; when one param resolves a failure, the finding names
that param and the outcome a rebuild predicted (section 2.4).

Every check exists because something failed. The seed note says it plainly:
"Each entry cites the failure that created it" (`hbf/seed/checks.seed.json`
line 2). A check with no failure behind it is a guess and does not enter
the registry (section 8).

### 1.1 CheckDef fields

Field names follow `spec/checks.ts`, which is the contract. The table adds
the rule each field obeys and the decision behind it.

| field | type | rule | decision |
|---|---|---|---|
| `id` | `CheckId`, `CHK-${CheckArea}-${string}` | matches `^CHK-[A-Z0-9]+-[0-9]{2}$`, unique across seed and entered rows, never reused after retirement; `CheckArea` is the 13 seeded prefixes plus ART and DEV (section 5) | D-066 |
| `version` | semver string | per check; section 1.3 | D-064 |
| `title` | string | one line stating what must be true, lowercase, voice-linted; the only statement of what the check proves (CheckDef has no top-level `what`) | D-004 |
| `appliesTo` | `{level: CheckLevel, kinds?: FeatureKind[]}` | `kinds` only with level `feature`, camelCase through `FEATURE_KIND_ALIASES` | D-017, D-065 |
| `severity` | `block`, `warn`, `note` | section 3; seed rows carry the same words, no mapping step | D-067 |
| `origin` | `CheckOrigin` | `{project, date, what, numbers?, knowledge?, evidence?}`; section 8 | D-064, D-066 |
| `needs` | `KernelId[]` | one union: profile, geom, mesh, 3mf, sim, circuit, copper, board, nest, inlay, motion | D-057 |
| `legalKind` | `interval`, `set`, `multipleOf`, `boolean`, `exactSet`, `none` | every check declares one; results must match it; `exactSet` is the expect-set form (section 10) | D-066, D-074 |
| `gates` | metric ids, optional | the Part IR metrics this check gates; a metric with no gate is labelled informational | D-075 |
| `constraint` | ConstraintDef id, optional | present when the legal values come from the solver, for example `sim/click-spring-window` | D-044, D-072 |
| `status` | `CheckStatus`: `seed`, `entered`, `registered`, `retired` | `entered` rows have an id, origin and page but no run body yet | M04-T12 |
| `pending` | `MilestoneId`, optional | the milestone that lands the run body; the seed conformance test requires it on every `entered` row | M04-T01 |
| `drivenBy` | `(target) => string[]`, optional | JSON pointers into params whose change moves the measured value; feeds Fix | D-064 |
| `run` | `(target, ctx) => Finding[]`, sync or async; the registry stamps id, version, severity, origin and waived into each CheckResult | pure over its inputs; no DOM in tiers S to 2 | D-045, D-206 |

Two `what` strings existed in the handoff and only one survives. The seed
row's `what` is the failure, and it lands in `origin.what`; that is the
field the M-1 step fills for the 14 rows that had it empty (section 8,
milestones/M-1-housekeeping.md step 5). The title states what the check
proves.

The types live in `spec/checks.ts` (compiled with the spec by `npx -y -p
typescript@7.0.2 tsc -p spec/tsconfig.json`, exit 0 on 2026-10-04); this
file links them and does not copy the bodies (D-179). In brief: `CheckLevel`
has ten members; `CheckOrigin` holds project, date, what, numbers,
knowledge and evidence; `ResultTarget` is a union with one member per
level, so a feature result always carries its feature id; `Evidence` ties
`measured` to `legal.kind`, and `CheckResult = CheckResultBase & Evidence`;
`CheckDef<L, K>` is generic over level and feature kind, with
`appliesTo.kinds?: readonly K[]`, and its `run` returns `readonly
Finding[]`, which the registry stamps with id, version, severity, origin
and waived to make each CheckResult; `AnyCheckDef` is `CheckDef<L, any>`
(D-206).

`TargetOf<L>` picks the `CheckTarget` variant for the level, so a check on
level `artifact` receives `ArtifactBytes` and a check on level `net`
receives the net and its part (section 4). The result's `target` is a
`ResultTarget` keyed by `level`, the same word.

`CheckCtx` carries the profile lookup with read tracking, the machine id,
whitelists keyed by mesh hash, and handles to the registered kernels
(`spec/checks.ts`). A check reads numbers through the profile, never as
literals, so a coupon that changes a profile row moves every verdict that
depends on it and the project graph marks those outputs stale
(milestones/M04-checks-project.md, M04-T09).

### 1.2 Where checks live

| what | where |
|---|---|
| seed rows (titles, versions, origins, legal kinds) | `packages/checks/seed/checks.seed.json`, the single source for those fields |
| run bodies | `packages/checks/src/defs/<family>/<id>.ts`, one module per check; kernel-owned checks (CHK-INL-01 to 04 in `packages/inlay`, the CHK-KEY-04 constraint in `packages/sim`) register through `RegistryEntry<'checks'>` at load |
| loader, skip rule, severity, nearest, fix, expect, capture | `packages/checks/src/{registry,loader,skip,severity,nearest,fix,expect,capture,origin}.ts` |
| fixtures | `packages/checks/test/fixtures/<id>/{pass,fail}.*` |
| generated pages | `docs/reference/checks/<id>.md`, `INDEX.md`, `origin-gaps.md` from `tools/gen-check-pages.mjs` |
| resource | `hbf://check/<id>` (D-050), printed by `hbf explain <id>` |

Package `checks` is tier 2 and imports spec, tier 0 and tier 1 only (D-044).

### 1.3 Versioning

Semver per check. The rule turns on one question: can the verdict flip on
the same Part IR?

| bump | when | examples |
|---|---|---|
| major | a verdict can flip on the same input | CHK-3MF-06 and -07 to 2.0.0 (the gold Flash Studio save fails the old titles, passes the new); CHK-KEY-04 to 2.0.0 (constant window replaced by FE interval); CHK-NET-05 to 2.0.0 (per-MCU interval); CHK-3MF-04 to 2.0.0 (pinch inset added); CHK-INL-01 and -03 to 2.0.0 (retargeted from `pocket` to `inlay`); CHK-SHT-03 at M07 (DXF reload rules from COTTER `audit_dxf.py`) |
| minor | new findings that only warn, or a severity change (it changes what export does, never the verdict) | a warn check moved to block |
| patch | message wording, origin text, retarget to a CheckTarget variant that reads the same data, a `needs` correction | the 19 project-level retargets (section 4); origin design renamed from HAFT to PIP |

The check version enters `registryHash` and `reportHash` (D-051), so a bump
marks every report that used the check as stale. A version never moves
without a CHANGELOG line in the seed's git history that names old and new
numbers when a number moved (D-005 body rule).

## 2. Results and messages

### 2.1 CheckResult

| field | content |
|---|---|
| `id`, `version` | the check and the version that produced the finding |
| `verdict` | `pass`, `warn`, `fail`, `skip` |
| `severity` | copied from the CheckDef so a reader of one finding knows what it blocks |
| `target` | a `ResultTarget`: the `level` plus part, body, feature, net, artifact or path, and a point `at` in mm when the failure has a location (locatable findings, D-125) |
| `measured` | the value the check computed, in the unit of `legal` |
| `legal` | LegalValues of the declared kind; intervals carry `nearest` |
| `constraint` | one line naming what set the legal values |
| `origin` | `hbf://check/<id>` |
| `fix` | present only when exactly one param drives `measured` |
| `extra` | numbers that are evidence but not the verdict: closest approach, volumes, pin voltages, predicted build hash |
| `waived` | present only when a chase `waive` entry turned a fail into this warn: `{reason, until?}`; measured, legal and fix stay as computed (section 10, D-173) |

A NaN or missing measured value is the error `E_PARAM_MISSING` with the JSON
pointer that was missing, never a fail verdict (D-064). The fixture is the
FEELER encoder fit, which read an undefined `P.armW` and reported a silent
not-ok (plan-deltas R53, `syn/plan-deltas.md` line 716).

A skipped check returns one result with verdict `skip`, legal `{kind:
"none"}`, the reason in `constraint` ("kernel circuit not registered (lands
M05)"), and its origin. A check that did not run is reported as not run,
never as pass (D-153).

The all-clear is a count, never a bare word (G-33). A report with no fail
and no warn renders as `<n> checks ran, <s> skipped: <families that ran>`,
for example `41 checks ran, 7 skipped: print, fit, net`. A build where no
check applied renders `0 checks ran`, never `all pass`. Origin: BLOCKS
2026-09-14 printed `manifold, nets and fits all pass (0 fits checked)` on
DECK, SLIDER, TOUCH, LAMP and RESISTOR (`notes/gold/blocks.md` F8). The
counts come from the report, so the text mirror, the CHECKS panel and the
status strip read one number.

### 2.2 Legal values and nearest

| kind | measured | nearest |
|---|---|---|
| interval | a number in `unit` | clamp toward the inside at the param's step: below `lo` gives the first step at or above `lo`; above `hi` gives the last step at or below `hi` |
| multipleOf | a number | both neighbours `[floor, ceil]` as multiples of `base` |
| set | a number or string | the closest member |
| boolean | true or false | none |
| exactSet | a set of target ids | none; the finding lists `missing` and `extra` (section 10) |
| none | anything | none; used for skips and informational notes |

Nearest follows D-064: the closest legal value to the measured one. The
midpoint of the band plays no part. For CHK-KEY-01 at a 2.15 mm gap
on a 3.20 mm cone the nearest is 1.60 (the band edge), not 1.44 (the 45
percent midpoint that `syn/api-library-ai-design.md` 6.3 printed); the
golden in milestones/M04-checks-project.md M04-T04 uses 1.60.

### 2.3 E_UNSAT

When the solver's floors exceed its ceilings the interval is empty. The
finding (or the `constraints.query` result) carries `legal: null`, every
bound with its kernel, reason and source, and an `E_UNSAT` error whose
`expected` names the smallest change that would fit. An empty interval is
an answer, so MCP returns it with `isError: false` and verdict fail; the
CLI exits 1 and HTTP is 200 (`ERROR_TRANSPORT` in spec/errors.ts, which
revises `syn/api-library-ai-design.md` 6.2 on this row).
Section 2.6 example C is the trace-width case (D-072, C-01).

### 2.4 Fix

`drivenBy` returns the param pointers that move the measured value. The
default implementation returns every ParamField whose `constraintDim` equals
the dim the check is backed by (D-132). With exactly one pointer, the
solver returns the param's interval with the build's facts, and `set` is
the nearest end of that param interval, in the param's unit; it equals
`legal.nearest` only when the check measures the param itself (D-064). The
interval rides along as `paramLegal`. The design is rebuilt in memory with that value, the same check runs
on the new Part IR, and `predicts` holds that run's measured value and
verdict; the predicted build hash goes in `extra.predictedBuild`. With zero
or two or more pointers there is no fix, and `next` names
`constraints.query` for the dims involved. A fix never points into geometry
(D-064). On a multipleOf tie, the neighbour whose predicted verdict passes
wins; if both pass, the larger.

### 2.5 Message template

One line states the failure; one line states the fix.

```
<what failed> <measured> <unit>, legal <set>, set by <constraint>
fix: set <param> = <value>, predicts <measured> <unit>, <verdict>
param: <pointer> legal <lo> to <hi>
```

When no fix exists the second line is `next: <command> <args>`. The text
mirror (`syn/api-library-ai-design.md` 6.3) renders the same content as a
block: status line, then per finding `measured`, `legal`, `because`, `fix`,
`origin`, in that order, FAIL findings first, then WARN, then NOTE.

Every number in a message is formatted from the computation that produced
it. `core/test/message-numbers.test.ts` parses every number from the
rendered text and JSON strings and requires each to equal a CheckResult
field, or a named derivation in `core/src/text/fmt.ts`, at its printed
precision (milestones/M04-checks-project.md M04-T05). Numbers inside the
origin line are quoted from `origin.numbers` with their qualifier and are
exempt. Measured values in findings are computed from Part IR unless the
finding says otherwise; a value read from the profile carries its tier.

A printed interval floor rounds up and a printed ceiling rounds down at the
printed precision, so every printed bound is legal; `core/src/text/fmt.ts`
owns the rounding.

## 3. Severity

Three values, the ones the seeds already carry (D-067). Severity says what a
fail of the check stops; verdict says what happened on one target. No
severity stops the build. Every build completes and stores its Part IR, so
a failing finding can be rendered, probed and located (D-125), and a fix
can be predicted by a re-run. A kernel that cannot produce geometry at all
returns `E_KERNEL`, a command error with no CheckResult.

| severity | effect of a fail | text mirror | assigned to |
|---|---|---|---|
| block | stops fabrication export: `export.run` exits 1 with the findings and never shows the gate prompt (D-109); `part.build` and `check.run` exit 1 and the IR stays in the store | FAIL | every seed row with `block`, and entered rows unless stated |
| warn | shown: verdict warn, exit 0 | WARN | every seed row with `warn` |
| note | informational: verdict pass or warn, printed as NOTE, exit 0 | NOTE | informational metrics (section 10) and stale-item notes from `rules.audit` |

Precondition checks. Seven block checks, marked `precondition: true` on
the CheckDef (spec/checks.ts), prove the solid, its topology and its
volumes. When one fails, the checks that read volume, topology or
per-body geometry of that target return skip with the reason "precondition
<id> failed" instead of a verdict computed on a wrong solid. The IR is
still stored and every other check still runs. This is a skip rule
(section 4), separate from severity.

| check | origin failure | what a fail makes unreliable |
|---|---|---|
| CHK-PRT-01 | COLLAR 2026-08: directed-edge balancing passed coincident faces; trimesh disagreed; CRESSET 2026-08-30: the shipped example has 40 + 16 + 1 edges shared by four faces although its README claims 0; PLINTH fixDiag removes them (plinth-sync32.3mf: 0) | a non-manifold solid has no defined volume |
| CHK-PRT-02 | COAMING 2026-08: coincident rings fused into 4-face edges | same |
| CHK-PRT-03 | COLLAR 2026-08: `validate_3mf --overlap` | overlapping bodies double-count material and break per-body checks |
| CHK-PRT-11 | OGEE R16-P 2026-08: four parts shrunk in one pose only | print pose and assembly twin are different solids |
| CHK-KEY-06 | PIP 2026-09: a flex cone kink on a cavity face exported a broken shell | broken shell |
| CHK-SHP-01 | DETENT rev D 2026-07-30: unbounded half-space cut a neighbouring sub-solid | a neighbour's geometry is wrong |
| CHK-SHP-04 | OGEE R16-M 2026-08: tangent weld became six bodies after the print shrink | body count is wrong |

Seed rows register with their severity unchanged; there is no mapping step.
Counts as of 2026-10-05: 77 block, 9 warn, 0 note over the 86 seeded rows
(85 and 76 block on 2026-10-04, verified-claims C6, before M-S-T06 seeded

Pair results (P-23). A check whose finding is about two targets at once
(CHK-PRT-03 overlap, CHK-ASM-04 and -11 clashes, CHK-ASM-07 closest
approach, CHK-ASM-12 and -13 when entered) returns `target: { level:
"pair", a, b, at? }`, where `a` and `b` are ResultTargets and `at` is the
contact point in mm. The viewer outlines both and frames the pair (G-35).
COTTER r5 2026-09-24 outlines one part of a hole clash; PIP r9 lists
fifteen collision and routing warnings with no place (`notes/gold/cotter.md`,
`notes/gold/pip-haft.md` flaw 8). `pair` is a ResultTarget kind only, never
a CheckLevel: the check still selects on its own level. The union member
lands in `spec/checks.ts` with the M04 retarget; until then these checks
put the second target in `extra.with`.

D-065 cites "25 artifact checks" from plan-deltas R53, which counted checks
needing any non-part target. After the retarget the seed has 7 artifact, 7
source, 2 page and 3 project rows (computed); the generated count wins.

Selection rule. The registry selects every check whose `appliesTo` level
has a target in the Part IR, narrowed by `kinds` at level feature, on
every build. A chase has no field that adds or removes a check; a model
that edits the chase cannot make CHK-NET-05 stop running on a conductor
(D-173). A chase states deliberate violations in `expect` and accepted
failures in `waive` (section 10).

### 7.6 Click and snap strain by bend direction (D-073, D-096, C-05)

Strain limits are stored per material with a bend direction and the method
`failure`, and every strain check reads the limit for the declared
direction. TDS elongation is not the basis; the PETG HF 8.6/5.1 elongation
figures are unverified (D-022).

| material | bend direction | limit | qualifier | source |
|---|---|---|---|---|
| PETG | in the layer plane | 2.5 percent | inferred (a ceiling set below the 2.7 to 3.3 percent the HAFT solver computed for beams that broke; D-191) | originals/pip/files/haft-src/src/model.js line 541 (fit click spring: eStop <= 0.025, PETG fatigues above about 2.5); `hbf/seed/profile.seed.json` line 140 (a 0.6 beam reached 2.7 to 3.3 percent and failed); `notes/latest/haft-toggle.md` line 261 (2.5 percent fatigue line); `fab-knowledge:research/3dp-landscape.md` lines 512 to 516 |
| PETG | across layers | 1.5 percent default (range 1.5 to 1.8) until a coupon | inferred | same, lines 512 to 516 |
| other materials | either | none until a row exists; the check returns E_PARAM_MISSING at the profile pointer | | D-102 rule for unprovenanced numbers |

Two checks read these rows:

- CHK-KEY-04 (section 7.4): eStop at the stop of the click spring against
  the limit for the spring's bend direction. PIP's beam bends in the layer
  plane.
- CHK-FIT-06, entered by this file (section 9): snap beam strain at full
  engagement against the same rows. The strain formula is the one PLINTH
  ships, `3 t d / (2 L^2)` with t the lip width, d the engagement and L the
  free length (`corpus/cresset-plinth/outputs/plinth.html` lines 2927 to
  2929); D-096 makes it the shared snap family formula. PLINTH's own
  bands (ok under 2.6, warn under 3.4 percent) are kept in the PLINTH
  mechanism's `derive()` to reproduce PLINTH and never decide a CHK-FIT-06
  verdict.

Worked case for CHK-FIT-06 (computed): lip width 1.2 mm, engagement 0.6
mm, free length 8.0 mm gives 3 x 1.2 x 0.6 / (2 x 8.0^2) = 1.69 percent.
Bent in the layer plane it passes (limit 2.5). Bent across layers it fails:

```
snap beam strain 1.69 percent, legal 0 to 1.50 percent, set by petg across layers, failure method (inferred)
fix: set /snap/freeL = 8.49, predicts 1.50 percent, pass
```

The fix value is the free-length floor sqrt(3 x 1.2 x 0.6 / (2 x 0.015)) =
8.485 mm, rounded up to the 0.01 step (computed); at 8.49 the strain is
1.498 percent.

### 9.11 From research: interlocking beams against a conductor

## 10. Expected-violation sets and capture assertions (D-074)

Deliberate violations and captures are declared data that a check verifies,
never hand exceptions.

Expect sets. A chase `expect` entry names a check and the declared set of
violations (pairs, nets or ids). The check computes its measured set over
the target and passes only when measured equals declared. The finding
lists `missing` (declared, not measured) and `extra` (measured, not
declared) in `extra`; drift in either direction fails.

| fixture | declared | measured from | expect |
|---|---|---|---|
| SHUNT G7 inverted gate | 5 shorts (P8V and N8V, BOOT, ANALOG, ENC, NANO), 5 floating nets (GND?, MAGIC, MATRIX, PROBE, VIBES) | `corpus/shunt/outputs/shunt-r1/board.json` `defects` (counted 2026-10-04) | pass |
| same, ENC removed from the declared set | 4 shorts | same | fail, `extra: ["ENC"]` |
| same, a sixth floating net declared | 6 floating | same | fail, the net under `missing` |

The SHUNT measured set at M04 comes from a list typed by hand in
`gen_board.py` lines 705 to 709, so the fixture is a contract fixture until
M08 extracts the nets from geometry and replaces it (D-089). Other expect
users from R53: SHIM `MULTI_ISLAND`, `CLEAR_EXEMPT`, `DECLARED_BRIDGES`.

Waivers. A chase `waive` entry `{check, target, reason, until?}` names one
check and one target id exactly, no globs (D-173). A fail on that pair
becomes verdict `warn` with `waived` set on the result, and the CHECKS
panel and the print card list it with its reason and end date. Rules:

| case | result |
|---|---|
| reason empty | `chase.validate` returns E_SCHEMA at `/waive/<n>/reason` |
| check id not registered | E_REF with `didYouMean` |
| check is a precondition check (section 3) | E_SCHEMA; a wrong solid cannot be waived |
| build date after `until` | the waiver lapses and the result is fail again |
| waiver matched no fail in this build | one warning naming the unused waiver, so stale waivers surface |
| check passes on the waived target | pass; the waiver is reported unused |

An expect set and a waiver differ in what they claim. `expect` says the
violation is the design and fails when it drifts; `waive` says a failure
is accepted for now and records who reads it later through the card.

Capture assertions. `capture {a, b, move, floorMm3}` passes when the
interference volume of a moved against b exceeds the floor. A capture is
how a snap, a trap or a retainer proves it holds.

| fixture | move | measured (computed 2026-10-04) | floor | expect |
|---|---|---|---|---|
| DERRICK bracket against its trap | lifted 1.5 mm | 33.44 mm3 (DERRICK README 33.4) | 1.0 mm3 | pass |
| DERRICK module | lifted 1.0 mm | 57.56 mm3 | 1.0 mm3 | pass |
| DERRICK retainer | over-twisted 8 deg | 26.75 mm3 | 1.0 mm3 | pass |
| DERRICK bracket | lifted 0 mm, declared as a trap | 0.00 mm3 | 1.0 mm3 | fail |

## 12. CHK-DEV-01 CLASP payload (C-17, D-093)

A CLASP frame carries at most 65535 payload bytes (uint16 length;
`lumencanvas/clasp/crates/clasp-core/src/frame.rs`). A JPEG published as
one frame shares that budget with the PUBLISH encoding of the address and
metadata. LOUVER enforces `CLASP_MAX_PAYLOAD - 96` = 65439 bytes, with the
comment "measured overhead is 61" (`corpus/louver-clasp/outputs/LOUVER/LOUVER.ino:134`,
read 2026-10-04). The knowledge base's "about 65470" (65535 - 61 = 65474,
computed) holds only for a short address and is retired (verified-claims
C14).

Rule. For each source that publishes a binary payload over CLASP:

- default: payload at most 65439 bytes (computed: LOUVER sets CLASP_MAX_PAYLOAD 65535 minus 96, `corpus/louver-clasp/outputs/LOUVER/LOUVER.ino:134`, `corpus/louver-clasp/outputs/LOUVER/clasp.h:31`);
- exact: when the publishing address is a literal in the source, encode an
  empty PUBLISH frame for that address with the CLASP codec, take its
  length as the overhead, and require payload at most 65535 minus that
  overhead. The finding names which form it used.

Target source; needs none (it reads source text and the codec in `link`);
legal interval in bytes with `lo` 0. Measured is the declared or computed
maximum payload (for LOUVER, `maxJpegBytes`). It runs from M13 when the
link package extracts the driver contract.

```
clasp jpeg payload 65474 bytes, legal 0 to 65439 bytes, set by 65535 minus 96 bytes publish overhead (LOUVER default)
fix: set maxJpegBytes = 65439, predicts 65439 bytes, pass
```
