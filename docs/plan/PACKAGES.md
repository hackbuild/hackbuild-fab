# Packages

Version 4, 2026-10-04. Part of the hackbuild-fab plan set; PLAN.md is the index.

This file holds one section per workspace package of hackbuild-fab, in
tier order, plus `kernel/`, `core/` and `apps/`. PLAN.md section 7 carries
the summary row per package; this file carries what a builder needs to
create, port and prove each one. Where a milestone card and this file
disagree on a file path, the card wins for that milestone; where they
disagree on an import edge or an owner, this file wins and the conflict is
listed in section 9.

hbf (working name) is the binary with CLI, MCP and HTTP transports. CHASE
(working name) is the typed design document. STYLUS (working name, was
FEELER) is the printed sensor design. PIP (was HAFT) is the published
print-in-place controller at hackbuild/pip-controller. tools.hack.build
(proposed) is the cookieless bench origin. Working names stay flagged in
the first PR body (D-012).

Every number carries a qualifier (measured, computed, vendor, inferred,
unknown) or names the file it comes from (D-007). Counts are as of
2026-10-04; generated by tools/counts.mjs from M-1 onward (D-010). Repo
paths are relative to the hackbuild-fab root.

## 1. How to read a package section

Every section uses the same table.

| field | meaning |
|---|---|
| tier | the tier in `tools/tiers.json` (D-044) |
| owns | the concern the package is the single home for |
| may import | the workspace packages it may depend on; anything else fails the CI `tiers` job |
| seed code | harvested code the port starts from, as a repo path after M-1 (M-1-T07 map) and the legacy evidence path |
| adopted dependency | the external library wired first, with its pin from D-040 or the milestone card |
| commands served | the hbf commands (D-106) whose `core/src/commands/*.ts` handler calls into this package |
| registries | which of the 11 RegistryKinds the package supplies entries to; `core` registers them at load (inversion, D-044) |
| parity target | the numbers that prove the port, each with its qualifier |
| milestone | where the package is created and where it reaches parity |
| extraction | whether and when it leaves hackbuild-fab (D-025) |
| inherited defects | the lineage failures the port must not carry, listed in the table under each section |
| decisions | the D entries that shape the package |

Evidence paths use the short roots below, expanded by plain prefix, the same
convention as MILESTONES.md.

| short | absolute path |
|---|---|
| hbf | `fab-knowledge:evidence/x/plan-to-refine/handoff/hbf/` |
| x | `fab-knowledge:evidence/x/` |
| syn | `fab-knowledge:synthesis/` |
| corpus | `fab-work-directory:` |
| repos | `hackbuild/` |

Example: `x/pip-controller/src/router.js` is
`fab-knowledge:evidence/x/pip-controller/src/router.js`.

The inherited-defect tables draw on syn/patterns-and-lineage.md section 4
and syn/mappings.md section 4.1, with every correction of
syn/verified-claims.md applied.

### 3.3 Registration by inversion

No package imports a registry it supplies. Each package exports plain
objects typed against `@hackbuild/spec` (`ConstraintDef`, `CheckDef`,
`FeatureKindDef`, `ExporterDef`, `MechanismDef`, `ArchetypeDef` and the
rest of `RegistryEntry<K>`); `core/src/registry.ts` collects them at load
and hands them to the registries (D-044, D-095). The constraint solver
therefore depends on no kernel, and a kernel package can own a check bound
to its internals (CHK-INL-* in inlay) without importing checks. 3mf is the
exception: it must split out standalone (D-027), so it exports plain rule
functions and the CHK-3MF-* CheckDefs that wrap them live in
`packages/checks/src/defs/3MF/` (5.1, 6.1).

### 3.5 Feature kind ownership

D-058 requires each `FeatureKindDef` to carry `generate`, non-empty
`checks`, `fit` (a function or `"none"`), non-empty `reference`, `schema`
and `version`. A FeatureKindDef lives in the lowest-tier package that can
generate its geometry; its checks are CHK ids resolved at registry load;
its physics (FE curves, resistance) lives where the physics lives and
reaches Part IR as metrics (D-049). Milestone cards M06 and M11 defer this
assignment to this file; it carries no D id yet (section 9).

| owner | kinds | first milestone |
|---|---|---|
| mesh | bore, pocket (with `sealed`, D-062), boss, chamfer, round, edgeProfile, window, web, tabSlot, snap, screw, hinge, horn, detent, finger, flexCut, lamination, bridge; admitted thread, bayonet, magnet, insert, spring, mount, relief | M00 stage runner with no kind; each kind at its `FEATURE_KIND_ADMISSION` milestone (D-058, D-177); latch moved to mechanisms, coupon to reference, pivot and pinInSlot to joints |
| circuit | conductor, contact, port (with `read`, D-078), pad | M05 |
| inlay | inlay | M03 |
| board | the board feature namespace of D-061 (outline, routed slot, NPTH mount, keepout, antenna keepout, silk string, art layer, registration mark, castellated seat with `holeDx`, solder jumper with declared default, mask opening, thermal slot, bare lead, declared bridge); these are `board-features.ts` members, outside the FeatureKindDef registry | M08 |

The spring kind is generated in mesh (the double-cosine beam body); its
force curve, drop and eStop come from `sim/src/fe/` as metrics, and its
window is the `sim/click-spring-window` ConstraintDef (D-071).
