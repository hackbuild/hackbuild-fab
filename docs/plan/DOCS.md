# Docs

Version 4, 2026-10-04. Part of the hackbuild-fab plan set; PLAN.md is the index.

This file is the doc architecture for hackbuild-fab: where each kind of
document lives, who or what writes it, and what proves it is still true.
PLAN.md section 18 carries the summary. Repo paths are relative to the
hackbuild-fab root; evidence paths are absolute.

hbf (working name) is the binary with CLI, MCP and HTTP transports. CHASE
(working name) is the typed design document, a TypeScript module. PIP (was
HAFT) is the published print-in-place controller, hackbuild/pip-controller.

Carries: D-001, D-003, D-004, D-007, D-008, D-010, D-022, D-026, D-031,
D-034, D-035, D-105, D-112, D-142, D-154, D-155, D-158, D-162, D-169,
D-170, D-171.

## 1. Rules every doc follows

| rule | what it means for docs | decision |
|---|---|---|
| rule zero | no AI or LLM credit in any doc, README, changelog, generated page, llms.txt, skill file or doc test fixture | D-001 |
| voice | repo register only, enforced by `tools/lint-voice.mjs` over every file under `docs/`, `knowledge/`, `.claude/`, every README and `llms.txt` | D-004 |
| qualifiers | every number in prose says measured, computed, vendor, inferred or unknown, with a source path or a generated marker | D-007 |
| verified block | every design README, reference README, package README with a passing parity target, the root README and every published post carries "What is verified, and what is not" | D-008 |
| derived numbers | counts and lists are generated; a count typed by hand is a defect the drift check finds | D-010 |
| unverified claims | the claims D-022 drops never appear in docs until a primary source is cited | D-022 |
| addresses | docs cite `https://hackbuild.github.io/hackbuild-bench/` for the device bench; `app.hack.build` has no DNS record and is never cited | D-031 |

The rules file (RULES.md) wins over this document wherever they disagree.

Four tutorials, each one outcome. Times are the api note's estimates
(inferred). Each is written at M10, once `chase.scaffold`, `chase.validate`
and `chase.render` exist, and becomes a required CI step at M11.

| file | outcome | starts from | asserts | depends on |
|---|---|---|---|---|
| `first-part.md` | a bored plate in PETG with one fit and one 3MF export, about 15 minutes (inferred) | `hbf chase.scaffold --kind single` with no `--from` | buildHash, reportHash with 0 fail, the fits.table row for the bore, artifactHash of the 3MF | M00 (3MF export), M01 (constraints), M10 |
| `first-printed-circuit.md` | `reference/keys/flex-pair` rebuilt from a blank chase | a blank chase | the reader's buildHash equals `reference/keys/flex-pair/expected/build.json`; CHK-KEY-01 passes at gap 1.44 inside legal 1.28 to 1.60 (computed); `circuit.solve` verdict per pin | M05 (reference admitted), M10 |
| `first-sheet.md` | a finger-jointed box in ply with a kerf coupon | a blank chase, process laser | coupon artifactHash, box buildHash, the finding that names an unmeasured kerf on `laser1220` (kerf null until measured, D-101) | M07, M10 |
| `port-a-bench.md` | COLLAR's legacy html turned into a chase, proven by the parity triple | `designs/collar/legacy/` with sha256 | `hbf parity designs/collar` exit 0: geometry matches, params round-trip, one edit gives the expected delta | M03, M10 |

### 4.1 Shape of a tutorial file

1. `# <outcome as a sentence>`, then one paragraph: what the reader makes
   and what they need installed.
2. Numbered steps. Each command sits in a fenced block with info string
   `sh tutorial`. Each file the reader writes sits in a fenced block with
   info string `ts file=<repo path>`.
3. After each command, the lines the reader should see, with hashes inside
   markers: `<!-- hash:first-part.buildHash -->` value `<!-- /hash -->`.
   The value comes from `docs/tutorials/expected/<name>.json`.
4. A last step that renders the part (`view.render`) and asks the reader to
   look at the PNG. The test checks that the PNG exists and its hash; it
   cannot look (D-154).
5. A "What this proved" list naming the checks that ran, by id, linked to
   their reference pages.

### 4.2 The tutorial test

`docs/tutorials/<name>.test.ts` (vitest 5.0.3):

1. Creates a temp workspace from the current checkout with an empty
   `.hbf/` store and `SOURCE_DATE_EPOCH` set to the value the determinism
   job uses (REPOS.md section 8.1).
2. Parses the tutorial in order. Writes every `ts file=` block, runs every
   `sh tutorial` block with `--json` appended, and asserts exit 0 unless the
   step's expected file says otherwise.
3. Compares every hash in the `--json` results with
   `docs/tutorials/expected/<name>.json` and with the markers in the
   Markdown. A mismatch in either place fails.
4. Runs `export.run` under a pseudo-terminal and answers the approval
   prompt, because the CLI gate needs a TTY and has no bypass flag (D-109).
   The helper is `tools/docs/pty.mjs`, wrapping `script -q /dev/null` on
   macOS and `script -qec` on Linux; it adds no dependency.
5. Reports "not run" with the reason when a step cannot run (missing
   wasm, no TTY helper), and exits non-zero (D-153).

The only updater for expected hashes is
`node tools/docs/tutorials.mjs --accept <name>`, which rewrites the expected
file and the markers together. A PR that runs it also changes a meshHash, so
the visual review checkbox applies (D-154).

## 6. Generated reference pages

One page per registry entry, for each of the 11 RegistryKinds in
`spec/registry.ts`: featureKinds, checks, constraints, exporters, simModels,
panels, adapters, profiles, motion, mechanisms, archetypes. References get
pages too, from `reference/INDEX.md` (D-105). Folder names are the kebab
form of the kind (`feature-kinds/`, `sim-models/`); profiles split into
`profile/material/`, `profile/machine/` and `profile/fit/` to match the
`hbf://profile/...` URIs.

### 6.1 Fixed sections

Every page has the same eight headings in this order. A heading that does
not apply reads "Does not apply to <kind>." so the test can check order
without special cases.

| heading | content | source |
|---|---|---|
| Summary | id, title, version, one-line purpose | the def |
| Schema | table of fields with type, unit and default | zod schema derived from `spec/` |
| Legal values | legal kind and how the bounds are derived, with the ConstraintDef id when one backs it | ConstraintDef, check `legalKind` |
| Checks enabled | check ids the entry turns on, linked | FeatureKindDef.checks, ExporterDef |
| Fit class | fit class id or `none` | FeatureKindDef.fit |
| Origin | design, date, failure, numbers with qualifiers, knowledge record id | check origin (M04-T02), canon provenance |
| Reference designs | reference ids that cover it, linked | `covers` fields (D-105) |
| Resource uri | the `hbf://` uri, or "none" for kinds without one | URI table in AGENT-SURFACE.md |

Kinds may append sections after the eight. Checks append drivenBy, version
history and run state at this commit (M04-T02 step 3). Mechanisms and
archetypes append the `derive()` source. Profile pages append the
provenance record (D-099) and the tier.

Only these kinds have resource uris today: check, feature-kind, archetype,
mechanism, reference, profile material, machine and fit, knowledge record.
Pages for constraints, exporters, simModels, panels, adapters and motion
print "none" until a uri is added to the URI table.

### 6.3 The coverage test

`tools/test/docs-coverage.test.mjs`, run by the `docs` CI job (section 13):

- loads every registry through the same loader `hbf` uses, collects ids
  per kind, lists the page files per folder, and fails on any id without a
  page or any page without an id;
- fails when a page's headings differ from the eight in 6.1, in order;
- fails when a Resource uri line differs from the uri the registry resolves;
- fails when a link inside `docs/` points at a file that does not exist.

The derived job regenerates all pages and fails on any
`git status --porcelain` diff (D-010).

### 9.3 The verified block

Heading `## What is verified, and what is not`, then the lists below, in
this order. Each list is a `###` heading whose text starts with its lead
line's words before the first comma or colon (`### Verified on this
machine`, `### Checked by machine on geometry`); the date, and for a print
the build, open each line of the list (`- 2026-10-05: <command> exit 0`),
because one list holds runs of several dates. The parser in
`packages/reference/src/readme.ts` (M11-T03) and the registry `verified`
field (M16-T05, D-158) read the headings by prefix. Every README with a
verified block uses this heading form (counted 2026-10-08: seven READMEs).

| lead line | maps to | who may write a line |
|---|---|---|
| `Verified on this machine, YYYY-MM-DD:` | `onMachine` | whoever ran it on that machine on that date, with the command |
| `Measured on a printed body, YYYY-MM-DD, on <build>:` | `measuredOnPrint` | a person who printed and measured it; the builder writes `none` (D-082) |
| `Simulated, YYYY-MM-DD, on <build>:` | `simulated` | the builder, citing the harness (`tools/slice/slice.mjs`, `tools/py/gcode/analyze.py`, the probe sim under `tools/skeleton/`) with every figure computed (D-235) |
| `Checked by machine, on geometry rather than hardware:` | `checkedByMachine` | the builder, citing the check id or harness and its exit code |
| `Not verified by anything:` | `notVerified` | anyone; every claim that has no line above goes here |

Rules:

- Each list is present except Simulated, which a README carries only when a
  virtual print ran on its design. An empty list reads `- none`.
- A simulated figure never moves into a measured list, and a virtual run
  never meets a step that asks for a printed body (D-234, D-235).
- PIP adds a fifth, dated list, "Measured on an earlier printed set". Any
  extra list whose lead line starts with `Measured on` maps to
  `measuredOnPrint` with its own date.
- A number in the block keeps its qualifier. A computed figure never moves
  into a measured list by dropping the word (D-007).
- A harness that did not run is listed under "Not verified by anything",
  never under "Checked by machine" (D-153).
- Published posts carry the same block (D-008); they are written outside
  this repo (section 11).

## 10. Knowledge records with stable ids

Knowledge is the explanation layer the tool reads. Its tiers (constants,
invariants, ordering rules, diagnostics, heuristics, taste) are in
`knowledge/README.md`, copied at M-1-T13.

### 10.1 Ids

- A record is a heading section or a table row in a file under
  `knowledge/`. Its id is `<file stem>#<anchor>`, for example
  `03-diagnostics#wrong-part-not-pose` and `motion-latch#latch-identity`
  (M12-T07, M16-T03).
- The anchor is explicit in the source, `<a id="wrong-part-not-pose"></a>`
  at the start of the heading line or the first cell of the row. Heading
  slugs change when text changes; explicit anchors do not.
- Ids are generated into `knowledge/INDEX.json` (sorted, committed) and the
  derived job fails on drift (D-010). The uri is `hbf://knowledge/<id>`.
- An id never changes once a check or a doc cites it. A record that moves
  to another file keeps its old id as an alias in `knowledge/INDEX.json`;
  deleting a cited record fails CI.

### 10.2 Both ways

| direction | where it is written | what proves it |
|---|---|---|
| check to record | the check's origin record field naming the knowledge id (M04-T02) | `npm test -w packages/checks -- origin`: every non-null id resolves to a record under `knowledge/` |
| record to check | `knowledge/ratchet.json`, generated: per record id, `enforcedBy` check ids and state (M16-T04) | the derived job; `motion-latch#latch-identity` lists CHK-MOT-05 |
| doc to record | links `hbf://knowledge/<id>` or `knowledge/<file>.md#<anchor>` in any doc | `docs-coverage.test.mjs` resolves every such link |
| error to record | `E_KERNEL` and `E_REPEAT` results carry a record id (M12-T06) | `hbf explain hbf://knowledge/<id>` exits 0 for each id in core/ |

A check with no record keeps a null record id and is listed in the
generated `docs/reference/checks/origin-gaps.md`. The page is the to-do list
for the ratchet; the rule that every check cites the failure that created
it stands.

## 12. Numbers in docs

### 12.1 Counts

Every count in docs, READMEs, llms.txt and the skill comes from
`docs/plan/counts.json`, written by `tools/counts.mjs` (M-1-T11). In prose
a count sits between markers that the generator rewrites:

```
<!-- count:checks.total -->85<!-- /count --> checks
```

`node tools/counts.mjs --write-prose` rewrites every marker. The derived
job runs it and fails on any diff.

### 12.2 Values quoted from goldens

A number quoted from a reference golden or a profile row uses a value
marker naming its source by JSON pointer, so the doc cannot lag the build:

```
<!-- val:reference/keys/flex-pair/expected/report.json#/results/0/measured -->1.44<!-- /val --> mm (computed)
```

The qualifier stays outside the marker and is checked against the source's
tier: a value from a row of tier inferred cannot carry "measured".

### 12.3 The doc-number drift check

`node tools/counts.mjs --check-prose` lists every number typed next to a
counted noun outside a marker (for example "85 checks"). Each key in
`counts.json` declares its nouns. M-1-T11 runs it as warnings; this document
sets when it blocks:

| scope | warns from | blocks from |
|---|---|---|
| `docs/` outside `docs/plan/`, every README, `llms.txt`, `.claude/skills/` | M-1 | M00 exit |
| `docs/plan/` | M-1 | never; a plan count must carry "as of YYYY-MM-DD" in the same sentence, and Appendix B is generated between `<!-- counts:begin -->` and `<!-- counts:end -->` |
| value markers (12.2) | M04 | M04 exit |

The plan set is a dated record, so its counts are snapshots with a date.
Everything else describes the repo as it is and has no date to hide behind.

The docs are Markdown files in the repo and read on GitHub until a host
exists. `fab.hack.build/docs` is the proposed address (REPOS.md section 12);
no DNS record exists on 2026-10-04 and every DNS change is the owner's
(D-034). No docs site generator is decided.

| state | address docs use | who changes it |
|---|---|---|
| today | repo paths on github.com/hackbuild/hackbuild-fab | nobody |
| Pages enabled on hackbuild-fab | `hackbuild.github.io/hackbuild-fab/docs/` (inferred from the bench pattern) | owner enables Pages |

baked bench (D-034).
