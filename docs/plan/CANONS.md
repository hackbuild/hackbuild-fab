# Canons

Version 5, 2026-10-05. Part of the hackbuild-fab plan set; PLAN.md is the index.

This file holds the two canon registries, `mechanisms` and `archetypes`,
entry by entry: their typed shapes, the seeded entries with status and
provenance, the corrections each entry carries, the four PIP (was HAFT)
buttons at PIP defaults, the 22 STYLUS (working name, was FEELER) THINPOT
candidates, `arch.apply`, and the coverage from canon id to reference id to
design. PLAN.md section 10 states the decisions; milestones/M06-canons.md
holds the cards a builder runs. Where this file and the M06 card disagree on
a step, the card wins; where either disagrees with spec/, spec wins and the
difference goes in the PR body.

Section 0 states the port rule of D-222: every entry ports from its
original's code and reproduces its geometry and feel. Section 11 names, for
every entry, the canonical original and the code location to port from and
the record that says how the original makes it.

hbf (working name) is the binary with CLI, MCP and HTTP transports. CHASE
(working name) is the typed design document. STYLUS (working name, was
FEELER) is the printed sensor design built from archetypes (D-164). The
circuit canon package is `archetypes`, formerly `circuits` (D-014). PIP is
hackbuild/pip-controller at b137deb, 2026-09-19 UTC, MIT (D-013).

Number rules for this file. Every claim about a body, a force or a
resistance carries a qualifier: measured, computed, vendor, inferred or
unknown (D-007). "Computed" numbers were rerun on 2026-10-04 with node
v22.12.0 from the named source, or come from the M01 and M06 cards, which
name their runs. Parameter defaults copied from a source are declared
values and carry the source path instead of a qualifier. Registry sizes are
as of 2026-10-04 and are generated by `tools/counts.mjs` from M-1 onward
(D-010); no count in this file is a test oracle.

## 0. Port rule: the originals are the source

Decided by D-222 (owner instruction of 2026-10-05). The rule binds every
entry in this file: seeded, added, candidate, stub or alias.

1. A canon entry is ported from the code of its canonical original: the
   file and function or lines section 11 names, which is the file
   `orig/INDEX.md` marks canonical and whose row in
   `orig/LINEAGE-ADD.json` (merged into the root `lineage.json`) has kind
   `canonical`. The port reproduces the original's geometry and its feel at
   the original's defaults: the same construction, the same fit rows, and
   the same force, click, detent, swing, strain and read readouts the
   original computes. Parity is the CLAUDE.md triple: geometry matches,
   params round-trip, and a one-param edit produces the original's delta.
2. The how-to-make source is the design's record, `orig/<slug>/RECORD.md`,
   byte identical to `knowledge/designs/<slug>.md` in the repo. The builder
   reads the record section that section 11 names before writing code, builds
   the part the way the record says the original builds it, and fixes what
   the record lists under "flaws a port must not copy" in the same
   milestone, with a `fixes` entry on the lineage row.
3. An entry is never reinvented. A governing relation, a default or a
   golden comes from running the original's code, never from a textbook
   form, a summary table, a seed string or memory. Where this file and the
   original's code disagree, the code is the source and the difference is
   listed in section 10.
4. Mockups are never a source. The fourteen generated mockups quarantined
   by D-222 are not read, cited or copied; no number, shape, layout, fixture
   or golden comes from them. The bar for a ported entry's bench and its
   reference renders is the original itself: a lit 3D stage of the real
   geometry, as in `orig/<slug>/shots/`, and the gold drives of D-212.
5. Where two originals carry one mechanism, section 11 names one canonical
   port source. The other is a variant whose record says why it was not
   chosen; its differences become params or presets of the one entry, never
   a second entry.
6. An entry with no original under `orig/` says so in section 11 and stays
   candidate (sao-port is community spec text; the TraceLab templates wait
   on the owner's provenance).

The spring buttons are the first case of the rule. flex-cone-key,
click-spring-key (with the SNAPFE force curve) and touch-comb-key port from
PIP `model.js` and `layout.js`; dome-button ports from THINPOT `domeCap`
with its flange lock collar, and its in-place cone `domeCone` is a variant
of flex-cone-key; the brick cone array ports from BLOCKS `parts.js`. Section
5 holds the PIP defaults and section 11 the file and lines for each.

## 1. Contracts

Two registries hold what the corpus proved (D-095). A mechanism is a
`MechanismDef` whose `derive()` computes its governing numbers in
TypeScript. An archetype is an `ArchetypeDef` whose `apply()` emits
features into a part and a record into `chase.applied`, and whose
`derive()` computes resistances at load from the profile (D-098). The
seed YAML equation strings, whose variable names did not match their
inputs, become docs text on `DerivedValue.equation` and on the static
resource `hbf://mechanism/<id>` or `hbf://archetype/<id>`.

Both registries register through `RegistryEntry<'mechanisms'>` and
`RegistryEntry<'archetypes'>` (spec/registry.ts). Both packages sit in tier
1 with an empty same-tier list, so they import only `spec`, `profile`,
`catalog`, `geom` and `mesh` (D-044). Interval rules the canons own are
exported as `ConstraintDef` objects and registered by `core` at load,
registration by inversion. Kernel files stay headless (D-045).

### 1.1 MechanismDef

The shape in spec/canon.ts as of 2026-10-04:

```ts
export type DerivedValue = {
  readonly value: number;          // in `unit`
  readonly unit: string;           // "mm", "N", "ratio", "deg"
  readonly equation: string;       // docs text, also served at hbf://mechanism/<id>
} & Qualification;                 // {qualifier, basis} from qualify() or qualifyRow()

export interface MechanismDef<P extends Readonly<Record<string, number>> = Readonly<Record<string, number>>> {
  readonly id: string;             // lowercase slug, "geneva-external"
  readonly version: string;        // semver; major when a derived value can change for the same params
  readonly family: string;
  readonly dof: number;            // degrees of freedom, count
  readonly params: SchemaLike<unknown, P>;
  derive(p: P, profile: ProfileLookup): Readonly<Record<string, DerivedValue>>;
  readonly governs: readonly string[];
  readonly failureModes: readonly string[];
  readonly processes: readonly Process[];
  readonly provenance: string;     // "TUMBLER 2026-08, KNURL 2026-09"
  readonly reference: readonly string[];
  readonly status: "typed" | "stub";
}
```

`derive()` is pure: no DOM, no profile writes, no clock. It reads material
numbers only through `ProfileLookup` (E, strain limit, friction), so a
coupon that changes a profile row changes the derived numbers and their
tier. Every output carries unit and qualifier; a test fails any field
without both (M06-T03).

Mechanisms also carry a generator where the source has one (the 18
TUMBLER modules emit sheet parts on the prism route; M06-T02). The
generator lives beside the def in `packages/mechanisms/src/` and returns a
`PartDraft` (spec/build.ts); the def does not hold geometry.

### 1.2 ArchetypeDef, ApplyIn and ApplyOut

```ts
export interface ApplyIn<P> {
  readonly draft: PartDraft;               // host part as build.ts declared it
  readonly face: FaceFrame;                // resolved for this build: origin mm, outward normal, in-face u
  readonly params: P;                      // validated, defaults filled
  readonly profile: ProfileLookup;
}

export interface ApplyOut {
  readonly bodies: readonly BodyDraft[];   // added bodies, local slot numbers
  readonly features: readonly Feature[];   // kinds admitted at the kernel milestone (D-177)
  readonly ports: readonly string[];       // local ids of emitted port features
  readonly slots: readonly MaterialSlot[]; // slots the bodies need, matched by material and role
}

export interface ArchetypeDef<P extends Readonly<Record<string, unknown>> = Readonly<Record<string, unknown>>> {
  readonly id: string;                     // "force-comb", "printed-rotary-pot"
  readonly version: string;
  readonly family: "printed" | "copper" | "board" | "printed-or-copper";
  readonly channels: number;               // read channels used, count
  readonly senses: readonly string[];      // "touch", "angle", "force"
  readonly emits: readonly FeatureKind[];
  readonly read: ReadModelKind;            // pullup | charge-release | adc | ratiometric | column-scan | ladder (D-078)
  readonly params: SchemaLike<unknown, P>;
  derive(p: P, profile: ProfileLookup): Readonly<Record<string, DerivedValue>>;   // resistances at load (D-098)
  apply(input: ApplyIn<P>): ApplyOut;                                             // pure, on a PartDraft (D-165)
  readonly limits: readonly string[];
  readonly tier: Tier;
  readonly provenance: string;
  readonly reference: readonly string[];
  readonly status: "proven" | "candidate" | "unproven";
}

// spec/ids.ts
export interface FaceRef {
  readonly ref: string;                    // face id build.ts declares, "body.top"
  readonly uv: Vec2;                       // offset from the face origin along u and v, mm
  readonly rotDeg: Deg;                    // rotation of u about the outward normal, deg
}

// spec/build.ts
export interface FaceDecl {
  readonly id: string;                     // unique per part, "<body id>.<face>"
  readonly frame: FaceFrame;               // this build: origin mm, outward normal, in-face u
  readonly extent?: Ring;                  // optional outline in the face frame, mm
}
// PartDraft.faces?: readonly FaceDecl[]; Author.face(id, frame, extent?) declares one

// spec/chase.ts
export interface AppliedArchetype {
  readonly archetype: string;
  readonly part: string;
  readonly face: FaceRef;                  // never absolute coordinates
  readonly params?: Readonly<Record<string, unknown>>;
}
```

Faces are addressable by construction. build.ts names the faces a
placement may land on with `k.face(id, frame)`, computing each frame from
params on every build, and returns them in `PartDraft.faces`. A placement
in `chase.applied` stores a `FaceRef`: a face id, an in-face offset and a
rotation. The kernel resolves it to a `FaceFrame` on every build (origin =
face origin + uv[0] u + uv[1] v; u rotated by rotDeg about the normal), so
when a param moves the face the placement moves with it. A stored world
frame would float or bury the archetype the first time brickH or a pad
height changed; spec/fixtures/negative.ts refuses one at compile time.
An unresolved ref is E_REF with didYouMean over the part's declared face
ids; a uv outside a declared `extent` is E_REF naming the face. Imported
and BRep parts declare faces the same way, so a part with no declared
face accepts no placement.

`apply()` runs on a `PartDraft`, never on a built `Part`, and returns
declarations that the kernel builds (D-165). One signature serves three
callers: the kernel's applied merge before stage 1, `Author.arch()` inside
build.ts (which may pass a `FaceRef` or a `FaceFrame` it computed from
params), and the `arch.apply` command. The merge, in `chase.applied` array
order, resolves the entry's `FaceRef` against the draft's faces, calls
`apply()` on the draft as build.ts returned it, maps each local slot to the
`chase.materials` entry with the same material and role, prefixes local
body and feature ids with `<archetype id>.<applied index>.`, and appends
the bodies and features to the draft. A dome button on a PETG lid therefore
adds its cTPU plug body and its cPLA pad bodies, and `arch.apply` adds the
cTPU and cPLA slots the lid chase lacked in the same patch. build.ts reads
placements with `Author.applied(partId)` only to make room for them, and
never re-applies them.

`apply()` emits bodies and features of kinds admitted at the kernel's
milestone (D-059, D-177) and nothing else. It never writes geometry directly and never
selects checks: the check registry selects checks by feature kind and level,
as it does for any part, so an applied archetype is checked by the same code
that checks a hand-declared feature (M06-T12). An archetype emits a `spring`
feature for its click spring; the sim FE computes the curve as a Part IR
metric at build (D-049).

`derive()` on an archetype returns the resistance of every declared
conductor path, computed from the profile row for that material and
direction (section 4.3). `tier` is not stored by hand: the registry computes
it at load as the lowest tier among every profile and catalog row the
archetype reads, and the stored field is that computed value.

### 1.3 Status values and the admission rule

D-097 lets an entry be typed or marked stub. M06 uses four statuses per
registry, defined in milestones/M06-canons.md "Status values used in both
registries". This file uses the same table.

| status | registry | meaning | derive and apply | reference |
|---|---|---|---|---|
| typed | mechanisms | governing numbers computed and reproduced against a harvested legacy source | run | written in M06 |
| proven | archetypes | as typed; apply reproduces the source's features and numbers | run | written in M06 |
| stub | both | registered with id, family and provenance; no harvested source proves a derivation | refused, E_REF naming the gap | none; listed as a gap |
| candidate | both | registered with params and provenance; promotion waits for a reference in a named later milestone | refused, E_REF naming the promotion milestone | none until promotion |
| unproven | both | demoted by a correction; the source design never implemented part of it | refused, E_REF naming the defect | none |

A refused entry is still findable: `mech.find` and `arch.find` list it after
the runnable entries with its status and reason. The M11 coverage test
counts every stub, candidate and unproven entry as a gap with its reason,
never as covered.

### 1.4 Worked example, type-checked

The example below is a `geneva-external` def and the load-time resistance
helper. It was type-checked on 2026-10-04 against a copy of spec/ with
`npx -y -p typescript@7.0.2 tsc -p tsconfig.json` (strict,
noUncheckedIndexedAccess, exactOptionalPropertyTypes; exit 0): the block
below as `x/tsc/canons/snippet.ts` with the import paths pointed at the
copy, and a runnable variant with a concrete schema as
`x/tsc/canons/canons-example.ts`.

```ts
import type { MechanismDef, DerivedValue } from "@hackbuild/spec/canon";
import type { ProfileLookup, ResistivityRow } from "@hackbuild/spec/profile";
import { lowestTier, qualify } from "@hackbuild/spec/profile";
import type { ResistivityDirection, Tier } from "@hackbuild/spec/ids";
import type { SchemaLike } from "@hackbuild/spec/schema";

/** n slots (count), d centre distance (mm), phi crank angle (deg). */
type GenevaParams = Readonly<{ n: number; d: number; phi: number }>;

/** The package derives this from zod; any Standard Schema v1 object fits. */
declare const genevaSchema: SchemaLike<unknown, GenevaParams>;

const out = (value: number, unit: string, equation: string): DerivedValue =>
  ({ value, unit, ...qualify([]), equation });

export const genevaExternal: MechanismDef<GenevaParams> = {
  id: "geneva-external",
  version: "1.0.0",
  family: "intermittent",
  dof: 1,
  params: genevaSchema,
  derive(p) {
    const rad = Math.PI / 180;
    const rp = p.d * Math.sin(Math.PI / p.n);
    const alpha = 180 - 360 / p.n;
    const theta = Math.abs(p.phi) <= alpha / 2
      ? Math.atan2(rp * Math.sin(p.phi * rad), p.d - rp * Math.cos(p.phi * rad)) / rad
      : Math.sign(p.phi) * (180 / p.n);
    return {
      rp: out(rp, "mm", "rp = d sin(pi/n)"),
      Rs: out(p.d * Math.cos(Math.PI / p.n), "mm", "Rs = d cos(pi/n)"),
      alpha: out(alpha, "deg", "alpha = 180 - 360/n"),
      dwell: out((p.n + 2) / (2 * p.n), "ratio", "dwell = (n+2)/(2n)"),
      index: out((p.n - 2) / (2 * p.n), "ratio", "index = (n-2)/(2n)"),
      theta: out(theta, "deg", "theta = atan2(rp sin phi, d - rp cos phi) within |phi| <= alpha/2"),
    };
  },
  governs: ["slots open to the rim", "locking disc scallops clear the crank at every angle"],
  failureModes: ["pin shears at entry without lead-in", "hub severed by bore plus pin hole"],
  processes: ["laser", "fdm"],
  provenance: "TUMBLER 2026-08 (tumbler.html:1217), KNURL 2026-09 (knurl.html:588 to 600)",
  reference: ["mechanisms/geneva-3"],
  status: "typed",
};

/** One declared conductor path of an archetype (D-098). Lengths in mm. */
export interface ConductorPath {
  readonly id: string;
  readonly material: string;
  readonly direction: ResistivityDirection;
  readonly lengthMm: number;
  readonly widthMm: number;
  readonly thicknessMm: number;
}

/** R = rho x 10 x L / (w t): rho in ohm cm, geometry in mm, R in ohm. */
export function resistances(paths: readonly ConductorPath[], profile: ProfileLookup) {
  const values: Record<string, DerivedValue> = {};
  const tiers: Record<string, Tier> = {};
  for (const p of paths) {
    const row: ResistivityRow = profile.resistivity(p.material, p.direction, "printed");
    const rho = typeof row.ohmCm === "number" ? row.ohmCm : row.ohmCm[1];
    values[p.id] = {
      value: (rho * 10 * p.lengthMm) / (p.widthMm * p.thicknessMm),
      unit: "ohm",
      ...qualify([row.provenance.tier]),
      equation: `R = ${rho} ohm cm x 10 x ${p.lengthMm} / (${p.widthMm} x ${p.thicknessMm}) [${row.id}]`,
    };
    tiers[p.id] = row.provenance.tier;
  }
  return { values, tiers, tier: lowestTier(Object.values(tiers)) };
}
```

A resistance is always qualified computed; `qualify()` puts the tier of
the row it read in `basis`, and the per-path tiers travel beside it. Dropping the tier to print a bare resistance would
promote an inferred row to a fact (D-007). For a range row the helper takes
the high end, which is the conservative end for a budget that sets a width
floor (D-072); the M06 resistance test asserts which end each archetype
uses.

`lowestTier([])` returns null, and `qualify([])` gives computed with basis
null, so the loader asserts that every archetype reads at least one row
before it trusts the computed tier. Board-family
archetypes read their catalog part rows (listing-derived parts are vendor
tier, D-102), so none reads nothing.

Run on 2026-10-04 (computed, node v22.12.0): at n 3, d 25 the def gives rp
21.650635 mm, Rs 12.500000 mm, alpha 60 deg, dwell 0.833333, index
0.166667, and theta -60, -53.8941, 0, 53.8941, 60 deg at phi -30, -15, 0,
15, 30 deg. These equal the M06-T04 goldens.

### 4.3 Resistance computed at load

An archetype declares each conductor path: width, thickness, a length
expression over its params, the material slot role, and the direction
(along, across, through). At load `derive()` computes R = rho x 10 x L / (w
t) per path, with rho in ohm cm from the profile row for that material and
direction and geometry in mm. The archetype's tier is the lowest tier among
every row it read, catalog pin rows included. One coupon that writes a
measured row therefore moves every dependent archetype's resistance and tier
on the next load (D-098).

Working rows are the D-081 working default: cPLA PIP preset 500 ohm cm
along and 2000 through, cTPU 400 (inferred, `x/pip-controller/src/layout.js:46`).
Yousu raw-filament figures (240 to 481 ohm cm, vendor) are never scaled onto
printed traces, and Nowka's printed figures apply to Protopasta only (C-09).
CHK-NET-05 warns while a row it reads is inferred. Seed resistances become
derived outputs; their old values stay in provenance as "seed, computed from
Protopasta 30 and cTPU 1500 on an assumed 1.0 x 0.72 section".

Golden, printed-rotary-pot arc at the seed section (arc_r 6.5, sweep 300
deg, 1.0 x 0.72; L = 34.0339 mm, computed):

| row | rho, ohm cm | tier | R, ohm (computed) | note |
|---|---|---|---|---|
| Protopasta cPLA printed XY | 30 | vendor | 14,181 | reproduces the seed's 14k |
| BOSS cTPU slot (Eel class) | 1500 | inferred | 709,040 | reproduces the seed's 709k |
| PIP preset cPLA along (working) | 500 | inferred | 236,347 | |
| PIP preset cTPU (working) | 400 | inferred | 189,077 | |

At the working rows the cTPU arc reads lower than the cPLA arc, which
reverses the seed's limit sentence ("a cPLA arc (14k) against 40k of printed
leads swings 10 percent; cTPU (709k) swings 73"). The swing becomes a
computed readout from the rows in force, and the reversal is a finding that
waits on the Yousu coupon (D-082).

Golden, buried-trace-stack per millimetre (computed): a 1.4 x 0.72 trace at
the PIP preset 500 ohm cm along is 4960.3 ohm per mm, so a 62 mm run is
307,540 ohm; the seed's 1.0 x 0.72 section at Protopasta 30 ohm cm gave
416.7 ohm per mm. PIP's drive rows (touch paths 0.91 to 0.93 Mohm, key
paths 1.5 to 1.72 Mohm, computed in `x/pip-controller/print/print-card.txt`)
are the full-path values the M05 circuit solve reproduces (D-079).

Propagation test (M06-T07): an in-memory ProfileLookup override, never the
profile data files, that sets the cPLA row to tier measured moves an
archetype that reads only cPLA to measured and leaves every archetype that
also reads cTPU at inferred.

## 7. arch.apply

`arch.apply` places one archetype on a named face of any part,
kernel-built, imported or BRep, emits its features into the part, and
records the placement in `chase.applied`, so every existing check runs
unchanged. The face is a declared face id plus an offset (`FaceRef`,
section 1.2), so the placement survives any param edit that moves the
face. It is
the operation the FAB app puts a mouse on at M15 (PLAN.md section 2.6).

Signature (spec/commands.ts):

```ts
"arch.apply": {
  input: { part: string; face: FaceRef; id: string; params: Params | null };
  output: {
    emitted: readonly string[]; ports: readonly string[];
    applied: AppliedArchetype; slotsAdded: readonly MaterialSlot[];
  };
};
```

Group author, MCP tool `arch_apply` (annotations BRANCH, not gated, D-107).
CLI form:

```sh
npx --no-install hbf arch.apply --part body \
  --face '{"ref":"body.top","uv":[0,0],"rotDeg":0}' \
  --id blocks-stud --params standard=boss-v1 --json
```

What it does, in order:

1. Resolve `id` through the alias table. Unknown id returns E_REF with
   didYouMean (exit 2). A stub, candidate or unproven entry returns E_REF
   naming the status and its reason or promotion milestone (exit 2).
2. Validate params against the def's schema and fill defaults. A missing or
   NaN param with no default returns E_PARAM_MISSING (exit 2). A param whose
   default an owner decision leaves open returns a typed question:
   `blocks-stud` without `standard` asks for `boss-v1` or `blocks-html`,
   since D-087's default is none until a print.
3. Run build.ts for the chase to get the host `PartDraft` named by `part`
   (E_REF if no draft has that id). Resolve `face.ref` against
   `draft.faces`: an unknown ref returns E_REF with didYouMean over the
   declared face ids (exit 2), a uv outside a declared extent returns
   E_REF naming the face. Then call
   `apply({ draft, face: resolvedFrame, params, profile })`. It returns `ApplyOut`: added
   bodies, features with body assignments, port ids and the material slots
   it needs. For `blocks-stud` the features are conductor (flange and
   post), contact (stud) and port (with its read model).
4. Write `{ archetype, part, face, params }` into `chase.applied`, with
   `face` as the `FaceRef` given, never the resolved frame, plus any
   slot from `ApplyOut.slots` with no `chase.materials` entry of the same
   material and role, as one patch on branch `hbf/<chase>` with the patch
   writer `chase.patch` uses: the anchor matches exactly once or the call
   returns E_STALE (D-115, D-132, D-165). Nothing is committed; commits
   happen when the owner asks (D-006).
5. Return the prefixed ids the next build will produce for emitted features
   and ports, the applied record, the slots added, and next calls
   `part.build` and `check.run`. `part.build` merges the entry into the
   draft before kernel stage 1 (section 1.2, spec/build.ts
   `APPLIED_MERGE`).

What it never does: write geometry outside the emitted features, select or
version a check, key a check on an archetype id, or write to the profile. A
CHASE (working name) carries the applied record as a declaration; the
conditionals live in the archetype's `apply()` (D-131).

M06 acceptance (M06-T12). A fresh PETG prism, `reference/conductors/blocks-stud-applied/`,
32 x 24 mm (4 x 3 studs at the 8 mm pitch) extruded 9.6 mm (BOSS brickH,
declared), declares `k.face("body.top", ...)` at z = brickH and gets a stud
at `{ ref: "body.top", uv: [0, 0], rotDeg: 0 }` with `standard: boss-v1`,
then with `standard: blocks-html`. The check registry selects by feature kind and
level; from the seed appliesTo the candidates are CHK-NET-03, CHK-KEY-01,
CHK-KEY-03, CHK-KEY-05 (contact), CHK-NET-04, CHK-NET-05 (conductor),
CHK-NET-10 (port), CHK-NET-01, -02, -06, -07, -11 (net) and CHK-NET-12
(project). The selected set and versions equal the set selected for
`reference/conductors/blocks-stud` at the same standard, per-feature measured
values for CHK-NET-03, -04 and -10 agree within 1e-6, and the card's diff
touches nothing under `packages/checks/src`. If the baseline shows a check
misfiring on a stud contact (for example CHK-KEY-01 returning
E_PARAM_MISSING on a contact with no coneH), the fix is an appliesTo change
with a version bump in its own PR under the M04 process, merged first.

A second golden in the same reference moves the face after the apply:
brickH goes from 9.6 to 12 mm with `chase.applied` untouched. It asserts
the `chase.applied` bytes are unchanged, the stud's flange base lies on
z = 12 within 1e-6 mm (no gap, no overlap with the brick body), the stud
centre stays at the top face centre within 1e-6 mm, and the same check set
and versions are selected. A third case edits the ref to "body.tpo" and
expects E_REF with didYouMean ["body.top"].

Commands that land with it at M06: `mech.find`, `mech.derive`, `arch.find`
(M06-T11). MCP projection at M12: `canon_search` covers mech.find, arch.find
