# UI

Version 4, 2026-10-04; gold revision 2026-10-05. Part of the hackbuild-fab plan set; PLAN.md is the index.

This file is the bench anatomy and the UX law for hackbuild-fab: which
design system the UI consumes, the tokens of record, the strips and
overlays every bench lays out, the interaction contract, the readouts
and findings a rail shows, the six kinds, the view system with the drive
pad, the law with the failure behind each line, the pink budget, the
mobile rules, the test hook, the bake, the acceptance replica,
accessibility, the performance budgets, and the gold acceptance
checklist (section 21). PLAN.md section 15 carries the decisions; this file carries the
detail a builder needs to implement them. The work lands in M09 (ui,
ui-core, bake, smoke), M10 (chase binding, kinds, glue counter, PIP
replica), M11 (kind coverage) and M12 (FAB app shell).

"Bench" in this file is the internal word for the layout a chase renders
into. User-facing copy never uses it as a generic noun, because BENCH is
the catalogue of hack.build tools (157 tools as of 2026-10-04 in
hackbuild-tools 2/MANIFEST.json, syn/verified-claims.md row 85); user copy says the tool name or "design". The
title suffix `NAME.bench` survives in headers. CHASE (working name) is the
typed design document (D-131). hbf (working name) is the binary. PIP (was
HAFT) is the published print-in-place controller at hackbuild/pip-controller
(D-013). tools.hack.build (proposed) is the cookieless bench origin of
D-034.

Number conventions. Pixel sizes, durations, colours and faces in the
token, primitive and mobile tables are design values read from the file
named in each table's source column; they are specifications.
Every other number says measured (with date and machine or file),
computed, vendor, inferred or unknown (D-007). Counts carry "as of
2026-10-04; generated by tools/counts.mjs from M-1 onward" (D-010).

Until the owner merges and publishes 0.3.0, hackbuild-fab installs a
`npm pack` tarball of the PR branch from `tools/vendor/` with its sha256
in `tools/vendor/SHA256SUMS` (M09-T02 step 9). When 0.3.0 is on npm the
dependency becomes the exact version and the tarball is deleted in the
same commit as the lock file and CSS lock change.

### 2.2 The CSS hash check

Bakes inline `dist/styles/hackbuild.css` with its `@import "./tokens.css"`
resolved inline. `fonts.css` is never inlined because it imports Google
Fonts. The bake writes `<style data-hb-ui="<version>" data-sha256="<hash>">`.
`tools/bake/ui-css.lock.json` holds the installed version and the sha256
of each inlined stylesheet. `tools/bake/check-ui-css.mjs` recomputes the
hashes from `node_modules` and from every baked file and exits 1 on any
mismatch (CI job `ui-css`, M09-T13).

### 2.3 What hackbuild-fab does not add

No headless component library, no declarative 3D layer, no Storybook. A
`/kit` route renders every component and panel in every state with
fixture data (`packages/bench/kit/` at M09, moved under `apps/fab` at M12).
One custom element, `<hb-viewer>`, because the viewer is used outside Vue
(baked benches, docs, the app). Revisit if the app becomes multi-user.
Native elements carry keyboard and ARIA behaviour; the four overlays the
corpus needs (HbModal, HbDrawer, HbDropdown, HbToaster) already exist in
hackbuild-ui (plan-deltas R24).

Decides: D-116, D-117, D-130

## 5. Shell family

One system, two densities of the same tokens and the same five faces
(D-120, owner default).

| Shell | Kinds | Chrome | Stage | Panels |
|---|---|---|---|---|
| `paper` | single, composer, surface, machine, catalog | paper with halftone (4 px, `rgba(26,26,26,.045)`), ink header with 3 px pink bottom rule, ink steps strip, sunk guide strip, ink status strip | void with the graph rule and `--hb-shadow-pink`; the lit set inside | raised paper rail; instrument heads (VT323 on an ink bar) |
| `instrument` | board, and live device views inside any kind | the same ink header and status strip | full-bleed void; no graph rule on PCB renders; bright lighting | floating ink panels with a 2 px `--hb-ink-border` edge and no shadow (an ink shadow on void computes 1.14:1); the edge carries the separation; VT323 heads and values; 10 px uppercase tracked labels in `--hb-lit-label` |

`BenchDecl.shell` declares it (`"paper" | "instrument"`, spec/bench.ts).
CONDUYT teal (`#5eead4`), JetBrains Mono and charcoal panels never appear
in fab; they belong to the CLASP and CONDUYT family and GUIDELINES says
the two languages never mix in one artifact. Doc figures (white, Inter
only) are a third language that never mixes with bench chrome. Client
brand packs (COTTER's HeatSync pieces) go into product geometry and paper
only; app chrome stays hack.build (D-147, owner default).

Keep 3D scenes brightly lit in both shells. Dark scenes that hid
silkscreen were rejected (GUIDELINES 6).

Texture: one per artifact, applied once at page level, never scrolling.
Halftone for benches and app chrome; the graph rule inside a stage only;
grain belongs to site pages and zines. No texture on a stage canvas, dial
plate, print or modal.

Decides: D-120

## 6. The skeleton

The skeleton is fixed. COLLAR, BLOCKS and PIP arrived at it independently
(ui-anatomy.md; plan-deltas R32 confirms it in BOSS, COTTER and PIP),
and all six gold benches ship it: ink header with a pink rule, numbered
steps strip with the current step underlined, guide strip with
`STEP N NAME` and one goal line, void stage with the graph rule, cams
top left, slot legend top right, raised paper rail of instrument panels,
ink status strip with worded lit chips; COLLAR is the `single` variant
with a right readout rail (gold section 1.7). A
kind (section 8) decides which regions exist and where the rail sits; a
chase names what goes in each region and never positions one.

### 6.3 The rail

- The stage legend is the colour key on every step (section 6.2) and
  collapses to status chips under 640. Materials and resistivity are a
  step pane, or a fold in the first step: swatch, slot (extruder)
  number, material with resistivity read from profile, which parts print
  in it, role. Art points at slot numbers, never at colours. Default in
  force for owner item gold P-21 (section 19): none of the six gold
  benches pins materials first, all six key colour on the stage legend,
  and BLOCKS gives MATERIALS its own second step because resistivity
  drives every readout. A material edit rebuilds every readout that
  depends on it within the commit (gold G-30: BLOCKS resistivity 30 to
  300 ohm cm rebuilt the lamp row in 23 ms, measured 2026-10-05).
- Each slot carries a preview colour (`MaterialSlot.preview`, hex) shown
  on the stage, the legend and the swatch. Default in force for owner
  item gold P-20 (section 19): the preview colour is also written as the
  3MF filament colour, as TANG, TOGGLE, COLLAR and COTTER do; the slicer
  may still override it. Colour edits are light commits and never
  rebuild (gold G-05).
- Then one pane per step (`RailStep`): instrument heads, rows, chips and
  declared panels (`PanelRef`: `materials`, `fits`, `checks`, `nets`,
  `hookup`, `exports`, `notes`, `coupon`, `params.<groupId>`,
  `plot.<id>`; M10 adds `type-picker` and `face-preview`).
- A group whose params move an electrical or mechanical figure ends in
  its readout grid (`ParamGroup.readouts`, gold P-03), after the rows and
  before the group's one note (section 6.6).
- A row shows only when it acts on the current design (`showWhen` with
  equals, not-equals, sets and any-of or all-of groups, gold P-01; gold
  G-41). A group may carry one fold of secondary rows and a row of group
  presets as chips (gold P-16: PIP's Yousu and Protopasta chips).
- A quantity the geometry computes is a readout, never an input; where a
  person expects an input, one line of `help` says why (PIP body
  thickness, "the largest need snapped to the 0.24 layer"). A numeric row
  with `auto` shows the derived value while it sits at the auto value
  (gold P-17, TOGGLE `body.studs`). A slot reference row lists the
  current slots by number and name and remaps with a log line when the
  slot count changes (gold P-19).
- A composer with an `instances` param (gold P-12) gets an inspector for
  the selected instance in the rail and a part list beside it, so every
  instance is selectable without hitting it on the stage (COTTER's only
  route to a hook is a hole 8.6 px wide at FRONT).
- Assembly knowledge renders as declared panels: HOOKUP (inline SVG
  schematic with computed resistor values), WIRING, YOU ALSO NEED,
  ASSEMBLY, FITS. These are the Maker's Bill of Rights in UI form.
- Type pickers are grids of rendered preview cards with nothing
  preselected.
- Repeatable groups (`list` params) carry per-instance type chips.
- Per-step actions live in the pane; global verbs live on the guide
  strip; nothing lives in both.
- The export step (PRINT or MAKE) opens with a coupon row when the
  build's `readsInferred` (`spec/commands.ts`, `InferredRead`) is
  non-empty. One row per coupon, never per inferred row. The coupon is
  the reference whose `CouponDecl.carries` (`spec/chase.ts`) covers the
  inferred rows, so loss and fit-band rows point at the fit gauge,
  resistivity rows at the four-wire coupon and kerf at the kerf coupon
  (PROFILE.md 11). Copy, with values from the build: `fits rest on an
  inferred loss row. print the fit gauge first, about <print.time> min
  (computed)`. The row carries one export button for that coupon built at
  this design's machine and material slots. The coupon export is a
  fabrication export and passes the same gate (D-109). The row never
  disables the design's own export buttons, because an inferred row warns
  and never refuses (PROFILE.md 2.2).
- The `coupon` panel (`PanelRef` `coupon`) is the step after a coupon
  prints. It lists the coupon's cells from its `build.json` with one tick
  group per cell (fit gauge: `slid`, `located`, `rocks`, `stuck`; kerf:
  the slot that fits; four-wire: a reading in ohm per bar). It shows the
  row the record would derive, with tier measured, method coupon, the
  machine, preset and conditions filled from the coupon build, before
  anything is written. Its one action emits the coupon record, never the
  row: in the FAB app a patch on branch `hbf/coupon-<coupon-id>` for the
  owner to commit (D-115); in a baked bench a file the person saves.
  Profile code derives the row from the record (PROFILE.md 11.1).
- A measured-input step (COTTER: two caliper numbers in, solved clip
  out) shows its readout live on `input`.
- Text fields patch the label in place with a 240 ms debounce and never
  re-render under the cursor (COLLAR).

### 6.6 Readouts

The person sets what the part should do; the bench solves the geometry
and reads the behaviour back off the built geometry (gold section 1.2:
TOGGLE set a contact tilt of 18 deg and read 18.00). Readouts are where
that loop shows, and every gold bench puts them at the foot of the panel
whose params move them (gold section 4).

A readout row is a label, a computed value in VT323 with its unit, and
where it matters a verdict keyed by a threshold. Declared as a `derived`
field with `fn`, `unit`, optional `limit` (min, max and the check id
carrying the same limit), optional `verdict` words and optional `focal`
(gold P-02), listed in `ParamGroup.readouts` (gold P-03).

| Gold row (verbatim) | Bench | What it shows |
|---|---|---|
| `3.3 kohm, 0.39 mA: visible` | BLOCKS lamp | value, current, verdict word |
| `7 % (281 counts)` | TANG pots | ADC swing in percent and counts |
| `strain at stop 4.13 %` in the error colour, behaviour `latches` | PIP click spring | value past a material limit, behaviour word |
| `a 45k internal pull up leaves the pin at 1.63 V` | TOGGLE hookup | the configuration to avoid, with the value it gives |
| `pause before layer 12` | COLLAR slicer | the derived number the printer needs |

| Rule | Value | Gold |
|---|---|---|
| placement | the grid sits at the foot of the group whose params move it, after its rows; cause and effect without scrolling | G-25 |
| recompute | every readout recomputes on every build; a material edit rebuilds every dependent readout within the commit | G-25, G-30 |
| verdict | a row with `verdict` renders the threshold word or sentence beside the value | G-26 |
| limit | a value past `limit` renders in the error colour (`--hb-err` on paper, `--hb-lit-err` on ink), and the same limit exists as a check named by `limit.check` | G-27 |

### 6.7 Findings and warnings

## 8. The six kinds

Six kinds, fixed: `single`, `composer`, `surface`, `board`, `machine`,

### 9.3 Notes have a home

Constraint notes are data (D-124). A sentence that qualifies one control
is `ParamField.help`: one lowercase line rendered as the label tooltip and
`aria-describedby`. A sentence about a panel goes in a declared `notes`
panel: at most one note per panel, one to three sentences, text from data,
passing `lint-voice --kind dom`. PIP's 16 `.note` elements map to these
homes in the M09-T09 table. A third home holds constraint notes that
carry a live number (COLLAR's `the flutes cut to r 19.50 but the rim
only reaches in to r 21.20`): a CheckResult bound to its field through
`ParamField.checks` (a list of check ids), rendered under the row with
the ok, warn or fail class and recomputed on every build; static help
stays in `help` (gold P-25, section 6.7). Every gold bench runs over the
one-note budget today (gold G-42), so the generator holds a rule the
gold benches do not. Note 11 carries a corrected number: Yousu raw
filament is 240 to 481 ohm cm (vendor) and is never scaled onto printed
traces; printed traces use the profile row, 500 along and 2000 through
(inferred), until a coupon is measured (D-081, C-09).

### 9.4 UI copy

Lowercase, terse, second person for instructions, naming the failure
mode. Check messages follow the error contract: `<what failed> <measured>
<unit>, legal <set>, set by <constraint>` then a fix line (CHECKS.md,
D-064). Confirms carry information. No exclamation marks, no emoji, no
dashes, no `Please` in check copy. Examples: `no board connected. plug in
usb and press connect.`; `3 connections could not be routed, widen the
body or move groups apart`; status chips `fits bed`, `mesh current`,
`2 warnings`.

The welcome's one-line note on every tool ends with `works from a file.
no account. your exports are yours.` (D-168). Each clause holds for a
baked bench: it builds offline from `file://` (D-129), nothing signs in,
and exports carry no claim (D-041). The smoke harness asserts the line is
present in the welcome text.

Decides: D-004, D-064, D-081, D-124, D-125, D-154, D-168

## 10. The pink budget

GUIDELINES "The one-accent rule": "If three things on screen are pink,
none of them are." The budget makes that rule countable.

| Class | Elements | Counts against the one |
|---|---|---|
| structural | header bottom rule, header title dot, current step underline, wordmark dot and `build`, the guide strip `STEP N NAME` label, the stage pink shadow, range `accent-color`, focus ring, the focused input's border and shadow, the busy meter segments while building, status strip top rule | no; shell components mark them `data-hb-pink="structural"` |
| focal | the primary action of the current pane, or the one live value the step is about, or the welcome primary start; declared per step as `RailStep.focus` | yes, exactly one per view |
| data | part colour `--hb-part-a` on the stage, a trace on a scope, `--hb-mask` on a PCB render | no; it is data on void inside the canvas |
| never pink | toggle chips (ink fill when on), HbSeg and HbTile on-states in a bench (ink fill, as toggle chips), HbRow is-on in the materials list (ink fill), secondary buttons, cam buttons (ink or ghost, current outlined), the header HbPill (is-ok or is-warn, never is-live), status strip tags (`.is-lit-ok` when good, `.is-lit-warn` when not), welcome step-grid numbers (ink), `<b>` in the status strip other than the focal value, card borders | must count zero |

Test (M09-T14, `tools/smoke/pink.ts`): for each step at 390, 768 and 1280,
plus the open welcome, count visible elements whose computed
`background-color`, any border side with non-zero width, or (for an
element with a direct non-empty text node) `color` is
`rgb(254, 3, 134)`, then subtract elements marked structural. More than
one remaining element fails and prints them; the count per view goes in
the report. A fixture page with two focal pink buttons must fail, and so
must a fixture page with one focal pink button plus a pink-text readout.

Legacy baseline: the PIP bench shows 10, 6, 6 and 7 pink-coloured
background or border elements on its four steps at 1280 before the
structural set is subtracted (measured 2026-10-04, M09-T14 step 5). The
legacy report records it and does not fail the job; legacy files stay
byte-identical (D-142).

The gold benches fail this rule today with 9 to 33 pink elements per
view (gold G-43, counted 2026-10-05). The generator holds the rule
anyway: gold sets the bar for behaviour, and the budget sets it for
colour.

Decides: D-125, D-142

## 12. The view system

Measured across the placed files and PIP (v3 section 10). The viewer
package ships every view so no bench reinvents one. Chases name views by
`ViewMode` (spec/bench.ts): `assembled`, `exploded`, `section`, `plate`,
`sheet`, `layers`, `iso`, `action`, `field`, `board2d`, `board3d`,
`silhouette`. Camera presets (`CamPreset`) and modes share the one cams

The 2026-09-15 FAB mockup set the view as independent axes: scope
(library, project, bench, agent), stage (`ViewMode`), camera
(`CamPreset`), render (solid, ghost, xray; ghost by default) and drive
(press, scrub, explode, section, step, run), with a rail and a tray
(`fab-knowledge:evidence/x/downloads/dl-boards-tools/fab/fab (2).html`

### 12.4 The drive pad

A stage overlay that is the stimulus: hold a key, tilt the stick, slide a
finger, and the mechanism animates while the readout shows the electrical
result. Clicking a target in the view drives it too. It is declared
(`views.drive`: `targets`, `gesture` hold, tilt, slide or stick,
`readout` from logic, ohm, settle, adc, travel, dir, pinV, pullupOhm,
force, pressure, tilt, `pickInView`, `pad`, `springMs`, `holdToggle`,
`chords`, `split`; gold P-05), never bespoke (M09-T10).

Two gold benches have one, and they are the two the owner names first
(gold section 3.2). TOGGLE is the reference for a tilt target, PIP for
hold targets. TANG's pads, pots and membrane slider are the targets a
generated TANG takes (hold for pads, slide for the membrane, rotate or
tilt for pots); BLOCKS keeps press, angle and touch in its SELECTED
panel and gains a pad from the same declaration.

| Rule | Value | Gold |
|---|---|---|
| exists | every design with a contact model has a drive pad | G-19 |
| position | bottom left; under 640 at most 25 percent of the stage, keys 44 x 44 px | G-52 |

Readout format, one line per held target, every number qualified:

For a tilt target the line leads with the pose and the lit contacts, as

coupon calibrated it, `uncalibrated` while the PIP default of 3500 us is
in force. The computed settle is never shown as the read time.

## 13. BenchHook

Every baked bench exposes one object on globalThis as `BENCH`
(`BENCH_GLOBAL` in spec/hook.ts), frozen in PIP's getter style (D-128).
Without it the smoke test cannot run and the bench is not done.

| Member | Type | Meaning |
|---|---|---|
| `ready` | getter, boolean | the first build finished and the hook is safe to drive |
| `state` | getter and setter | returns the design; setting replaces it, clamps every value to its declared range with one log line per clamp, and rebuilds (gold P-07, G-10) |
| `model` | getter | the last built model |
| `rev` | getter, count | increments on every commit |
| `built` | getter, count | rev of the last completed build |

## 14. The bake and three.js

### 14.1 The bake

Every design produces one offline HTML file from a per-design asset
manifest, `bake.json` beside the design or reference, through
`tools/bake/bake.mjs` (M09-T13; M10 wraps it as `chase.bake`). The seed is
pip/tools/build_bench.py plus the COTTER baker features (ESM manifold
converted to a classic script with `import.meta.url` replaced and
`export default Module;` asserted, base64 wasm, inlined fonts, a dash
assert, and an exactly-one-match assert on every replacement;
x/cotter-src/tools/build.py).

| Rule | Value |
|---|---|
| determinism | same sha256 on a cold rebuild; no timestamps, no absolute paths, LF endings, manifest order; CI job `bake-determinism` compares two clean runs |
| size | at most 16777216 bytes (16 MB) per file; the bake fails above it |
| network | zero requests off `file:` and `data:` at load; a `<script src=` or `<link href=` pointing off the file fails the bake |
| workers | no blob or module Workers; smoke wraps the `Worker` constructor and fails on a `blob:` URL or `type: "module"` |
| fonts | five faces as woff2 data URIs (D-121 default): Permanent Marker 400, Special Elite 400, VT323 400, IBM Plex Mono 400, 500, 600, 700, Libre Baskerville 400 italic, from @fontsource packages pinned exactly |
| CSS | hackbuild-ui stylesheet inlined and hash-locked (section 2.2) |
| assets | only what the manifest names; build_bench.py injected unused assets, so the manifest is explicit |
| CSP | a meta Content-Security-Policy as the first child of `<head>` (section 14.5); the bake fails without it |
| hosting | GitHub release assets and hackbuild-fab Pages until a cookieless origin exists (tools.hack.build, proposed); never on the signed-in `.hack.build` cookie origin (D-034, owner default) |

PIP parity proves the bake before fab bakes use it: the PIP legacy
manifest must reproduce pip/pip.html byte for byte, sha256
`a1fa88bd6ffa603c76059567c8b27c804536e39e7c07ec56c58daad55b001263`,
1924558 bytes (measured 2026-10-04 on the shipped file; a cold clone, `npm
ci` and `./build.sh` reproduced it, syn/verified-claims.md row 19).

### 14.2 What file:// allows

| Fact | Consequence |
|---|---|
| a module or blob Worker cannot load under file:// | manifold-3d 3.5.4 runs on the main thread as a classic script; long builds stay off the input path through the 320 ms debounce and the single build runner |
| wasm cannot be fetched or imported from a file URL | wasm ships base64-embedded in a classic script assignment (`wasm: { from, global }` in the manifest) |
| inline `<script type="module">` runs | three 0.186.1 is bundled into the entry module and inlined as one module script |
| `fetch` of a sibling file fails | every asset is inlined; decoders a design needs are inlined too |
| `CompressionStream` works | the share link compresses in the page with no library |
| `localStorage` may throw or be absent (private windows, blocked storage) | the storage wrapper catches, logs once per session, and the bench still boots (section 15) |
| https `import()` and CDN fetches would work | forbidden by the zero-network rule |

### 14.3 three.js

three 0.186.1 (r186). npm 0.186.0 is dated 2026-09-08; 0.186.1 matches
the 2026-09-24 GitHub release (syn/verified-claims.md row 125). r185
removed the Draco encoder and the Lottie and TTF libs and kept the
decoders; Draco, Basis and meshopt decoders still ship in r186. A bake

### 14.4 Supported browsers

The UX law targets the phone at the printer (390 px), which in practice
includes iOS Safari, and a bake opens from file://, whose rules differ by
engine. Support is stated per feature so a bench never half works in
silence.

| Feature | Chromium current and previous | Safari current (macOS, iOS) | Firefox current | Tested by |
|---|---|---|---|---|
| open a baked bench from file:// | yes | yes | yes | `browser` (Chromium, push); `browser-all` webkit and firefox projects (nightly) |
| edit, rebuild, undo, share link | yes | yes | yes | same |
| export 3MF, STL, DXF, SVG, card | yes | yes | yes | same; bench and node parity (TESTING.md 8.4) runs in Chromium only |
| touch at 390 px | yes | yes, by a person on a real iPhone (TESTING.md 15.3) | yes | Chromium touch-only project; WebKit overflow pass at 390 |
| link: WebSerial, WebUSB device panels | yes | no | no | `browser`; other engines report not run |

Where a link panel cannot run, the panel shows one line in place of its

other region of the bench still works. Playwright WebKit on Linux is an
engine approximation, so "yes" in the Safari column is a nightly WebKit

file:// failure found in WebKit or Firefox is recorded as a sub-row of
RISKS.md R-19 with the engine, the bench and the fact that failed.

### 14.5 Content-Security-Policy

Every baked file carries one policy in a meta tag, written by the bake as
the first child of `<head>` so it governs every script after it:

```html
<meta http-equiv="Content-Security-Policy" content="default-src 'none'; script-src 'self' 'unsafe-inline' 'wasm-unsafe-eval'; style-src 'unsafe-inline'; img-src data: blob:; font-src data:; connect-src 'none'">
```

| directive | why |
|---|---|
| `script-src 'unsafe-inline' 'wasm-unsafe-eval'` | every script is inline; `'wasm-unsafe-eval'` allows WebAssembly compilation and nothing else; manifold-3d 3.5.4 bindings run under a CSP without `unsafe-eval` (vendor, PR 1851, research/code-cad-and-eda-tooling.md:128), so `eval` and `new Function` stay forbidden |
| `connect-src 'none'` | enforces the zero-network rule of 14.1 in the browser as well as in smoke; it also refuses `fetch` of a `data:` URL, so the bake hands wasm to the module factory as bytes (`wasmBinary`) and never widens this directive to make a glue fetch pass |
| `default-src 'none'` | Workers, frames, media and objects stay refused, matching the no-Worker rule |
| `font-src data:`, `img-src data: blob:` | inlined woff2 faces; data images and blob previews of exports |

A link-enabled page (M13, capability `requires` per D-161) adds to
`connect-src` only the origins its manifest declares under `connect`, for
example the CLASP relay it talks to, and nothing else. Web Serial, WebUSB
and Web Bluetooth are not fetch requests and need no CSP entry. A meta
policy cannot set `frame-ancestors`; the cookieless host of D-034 sets that
as a header when one exists.

Smoke installs a `securitypolicyviolation` listener before load and fails on
any violation (TESTING.md 2.5). `'wasm-unsafe-eval'` is honoured by every
engine in the 14.4 table at its current version (vendor). Whether the current manifold glue fetches a
`data:` URL is unverified until M09-T13 bakes the first fab bench under this
policy.

Decides: D-034, D-121, D-127, D-129
